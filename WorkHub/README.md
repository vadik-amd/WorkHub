# Work Hub

Фоновое приложение (.NET 10, иконка в трее), которое запускается вместе с Windows и
работает постоянно. Два модуля:

1. **Запись созвонов** — пишет любой звонок (Zoom, Slack, Teams в браузере и т.д.) в
   один WAV-файл, оптимизированный под расшифровку **Whisper**; есть авто-детект по
   микрофону и ручной старт/стоп. Плюс встроенная транскрипция через Whisper.
2. **Автозапуск программ** — при старте хаба сам запускает заранее настроенные файлы
   и ярлыки, по желанию **от имени администратора**.

## Меню трея

| Пункт | Что делает |
|---|---|
| Статус | Ожидание / Идёт запись |

| **Автозапуск программ** → Настроить список… | Окно управления списком программ |
| **Автозапуск программ** → Запустить программы сейчас | Запустить список немедленно |
| **GlobalProtect** → Авто-реконнект… | Переподключать VPN при потере интернета (см. ниже) |
| **GlobalProtect** → Обновить подключение сейчас | Ручной Refresh Connection |
| Расшифровка (Whisper) | Транскрипция записей (см. ниже) |
| **Текст с экрана записи** | OCR записи экрана → timeline «что показывали» (см. ниже) |

| Авто-запись по микрофону | Вкл/выкл авто-детект |

## Модуль 1. Запись созвонов

### Формат (под Whisper)

- **Один WAV на созвон**, 16 кГц, 16-бит — родной формат Whisper (минимальный размер,
  без потери точности).
- **Стерео с разделением голосов:** микрофон (вы) → левый канал, системный звук
  (собеседники) → правый. Без клиппинга; Whisper при загрузке сводит в моно и слышит
  всех, а каналы при желании легко разделить.
- Нет микрофона → пишется моно (только системный звук).

### Откуда берётся звук

- **Собеседники — со всех устройств вывода сразу.** Звонилки часто играют не на
  «устройство по умолчанию», а на «устройство связи по умолчанию»: например, Slack или Zoom
  выводят звук в AirPods, а по умолчанию стоят динамики ноутбука. Поэтому захватывается
  loopback каждого активного выхода, и всё сводится в правый канал. Раньше писался только
  выход по умолчанию, и в такой ситуации правый канал оставался пустым.
- **Новые устройства подхватываются на ходу.** Раз в 3 с список выходов пересканируется:
  подключили наушники посреди созвона — их звук пишется с этого момента; отключили —
  захват снимается без обрыва файла.
- **Микрофон — тот, который открыла звонилка.** Это устройство записи, на котором есть
  активная сессия другого процесса; предпочтение отдаётся «устройству связи по умолчанию».
  При ручном старте, когда микрофон никто не держит, берётся устройство связи по умолчанию.
- **Лог:** `%APPDATA%\WorkHub\logs\recorder.log` — какие выходы и какой микрофон
  попали в каждую запись.

### Разделение созвонов и имена файлов

Каждый созвон — отдельный файл с временной меткой:

```
Документы\CallRecordings\
  call_2026-09-11_14-30-05.wav
  call_2026-09-11_16-12-40.wav
```

В авто-режиме каждый новый созвон пишется в свой файл; пауза до 4 сек внутри разговора
файл не разрывает.

### Режимы

- **Авто** (по умолчанию): раз в секунду проверяет, занят ли микрофон другим процессом;
  занялся → старт, освободился на 4+ сек → стоп.
- **Ручной**: правый клик по иконке → «Начать / Остановить» (или двойной клик).

### Запись экрана (по желанию)

Пункт **«Записывать экран вместе с созвоном»** (выключен по умолчанию). Когда включён,
одновременно со стартом записи созвона пишется и экран (основной монитор) в MP4 рядом с
WAV: `call_…​.mp4`.

- **Видео** снимается через ffmpeg (`gdigrab`) и кодируется аппаратно (`h264_mf`,
  Media Foundation) — грузит не CPU, а системный/встроенный кодировщик.
- **Звук** не берётся с экрана: в MP4 **вклеивается наш готовый стерео-WAV** созвона
  (мик+система) — поэтому не нужны ни виртуальные аудиоустройства, ни драйверные трюки.
- ffmpeg хаб скачивает сам при первом включении (~170 МБ, один раз, без установки/админа)
  в `%APPDATA%\WorkHub\tools\ffmpeg`.

> **Про «незаметность».** Обычная OS-запись экрана не детектится Zoom/Slack/Teams и не
> уведомляет участников — это не встроенная запись конференции. Никаких обходов защиты
> контента (`WDA_EXCLUDEFROMCAPTURE`) хаб не делает; окна, которые приложение само
> помечает как защищённые, в записи будут чёрными — это ограничение Windows, не баг.

Настройки в `settings.json`: `RecordScreen`, `ScreenAllMonitors` (все мониторы vs
основной), `ScreenIncludeAudio`, `ScreenFps`, `ScreenVideoBitrate`, `ScreenEncoder`,
`FfmpegExe`.

### Текст с экрана записи (по желанию)

Подменю **«Текст с экрана записи»** (выключено по умолчанию) достаёт из уже записанного
`call_….mp4` **текстовый timeline: в какой момент что показывали на экране** — чтобы
отдать его модели вместе с расшифровкой звука.

```
Распознать последнюю запись экрана
Распознать все новые записи экрана
Выбрать MP4…
⏹ Остановить распознавание
─────────
Что делать с записью экрана ▸  ○ Ничего  ○ OCR  ● OCR + кадры  ○ OCR + локальная VLM
Распознавать сразу после созвона   [ ]
Языки OCR ▸                        ← языки, установленные в Windows
Локальная VLM-модель ▸             ← Скачать модель… / список моделей / устройство
─────────
Открыть папку записей / Открыть лог
```

> **Это зрение, а не доступ к чужому приложению.** Экран во время созвона шарит **другой
> участник**: на нашу машину его содержимое приходит **только как видео-пиксели** внутри
> окна Zoom/Teams/Meet/Slack. Поэтому здесь принципиально нельзя использовать UI
> Automation или дерево доступности (у чужого приложения его тут нет — это картинка),
> нельзя опираться на `GetForegroundWindow`/имя процесса (вернёт «Zoom», а не то, что
> показывают), и курсор в кадре — курсор докладчика, а не наш (`GetCursorPos` вернул бы
> наш). Вся фича работает по пикселям записанного MP4 — это OCR, и ничего больше.

**Как выбираются кадры.** Шаринг почти статичен, поэтому кадры берутся *по смене
картинки*, а не по часам: видео прореживается до ~1 к/с, и кадр сохраняется, только если
он заметно отличается от предыдущего (ffmpeg `select='gt(scene,…)'`). 90 секунд реального
экрана дали 10 кадров, 40-минутный созвон обычно даёт десятки, а не тысячи.

- Порог `ScreenSceneThreshold` по умолчанию **0.02**, а не «общеизвестные» 0.3. Замеры на
  реальной смене слайдов: scene score ≈ **0.035–0.055**; при 0.3 из четырёх слайдов
  извлекался бы один. Порог 0.3 ловит только полную смену картинки (камера → демо).
- Детектор ffmpeg считает разницу **гистограмм**, поэтому перемещение курсора или окна
  кадров не порождает — реагирует именно смена контента. Это ровно то, что нужно.
- `ScreenMinSecondsBetweenFrames` (5 с) и `ScreenMaxKeyFrames` (400) страхуют от взрыва
  числа кадров на очень длинном или «мигающем» созвоне.

**OCR — Windows.Media.Ocr**, встроенный в Windows: полностью оффлайн, ничего не
скачивает, ~25 мс на кадр. Движок спрятан за интерфейсом `IScreenTextEngine`, так что
позже его можно заменить (RapidOCR / PaddleOCR-ONNX) без переделки пайплайна.

- **Язык решает всё.** Английский распознаватель читает русский слайд как
  `nnaHbl I-la cneAYlOU4VlVl KBapran`, русский тот же кадр — как «Планы на следующий
  квартал». Поэтому каждый кадр прогоняется всеми включёнными языками, и побеждает тот,
  чей *собственный* алфавит реально нашёлся на кадре; если кириллицы нет — берётся
  латинский результат (он точнее: `Owner`, `2.` вместо `0wner`, `З.`).
- На смешанном экране (русский интерфейс + английские термины) выигрывает русский движок,
  и латинские слова могут пострадать (`Home` → `Ноте`). Смысл сохраняется; если важна
  точность латиницы — оставьте в «Языки OCR» только английский.
- Языки OCR ставятся в Windows: **Параметры → Время и язык → Язык и регион → нужный язык
  → Параметры языка → Оптическое распознавание текста**. Что уже установлено, видно прямо
  в подменю «Языки OCR».

**Что получается.** Рядом с видео появляются:

```
Документы\CallRecordings\
  call_2026-09-28_10-16-06.mp4
  call_2026-09-28_10-16-06.screen.txt    ← timeline для человека
  call_2026-09-28_10-16-06.screen.json   ← то же для модели (+ ссылки на кадры)
  call_2026-09-28_10-16-06.frames\       ← ключевые кадры (в режимах «+ кадры» и VLM)
```

```
## [00:00:00 – 00:00:06]  (en-US)
Quarterly Planning — Q4 2026
Roadmap review
1. Agent Gateway migration

## [00:00:12 – 00:00:18]  (ru)
Планы на следующий квартал
Задачи команды платформы:
- перенос шлюза агентов
```

Подряд идущие кадры с одинаковым (или почти одинаковым — сходство ≥ 0.9 по триграммам)
текстом не дублируются: блок просто расширяется по времени. Кадры без читаемого текста
(камера, тёмный экран) не создают пустых записей.

#### Три режима — и какой выбрать

| Режим | Стоимость | Что даёт |
|---|---|---|
| `ocr` | 0 МБ, ~25 мс/кадр, оффлайн | Плоский текст с таймкодами |
| `ocr+keyframes` | 0 МБ, ~50 КБ на кадр | То же **плюс сами кадры** — их смотрит мультимодальная модель (Claude) и описывает приложение и структуру экрана лучше локального VLM |
| `vlm` | 2–8 ГБ весов вручную, секунды-минуты на кадр | Локальное текстовое описание каждого кадра |

**Рекомендация — `ocr+keyframes`.** Конечный потребитель этих данных (Claude) сам
мультимодален: ему можно отдать `.screen.json` вместе с кадрами, и он опишет интерфейс
точнее любой локальной модели, не требуя гигабайтных загрузок. Локальный VLM оправдан
только когда доступа к внешней модели в рантайме нет, нужна оффлайн-структура экрана или
приватность запрещает выгружать кадры.

#### Слой 2: локальная VLM-модель (опционально)

Режим `vlm` добавляет к OCR описание каждого кадра («что за приложение, что происходит»)
локальной vision-language моделью через **OpenVINO GenAI `VLMPipeline`** в
Python-сайдкаре `ov_screen_vlm.py` — по образцу того, как работает `ov_whisper.py`.

- **Устройство** настраивается; `AUTO` пробует **NPU → GPU → CPU**, молча падая на
  следующее при ошибке инициализации и записывая в лог, что реально используется.
- Модель загружается один раз на всю пачку кадров (загрузка дороже распознавания);
  кадры передаются сайдкару как raw RGB (в venv нет библиотеки изображений, а raw не
  требует согласия сторон о кодеке).
- Нет модели или она не грузится → слой просто не активируется, в лог пишется причина,
  и работает обычный OCR.

**Модель качается из приложения** — так же, как модели Whisper: **«Локальная VLM-модель» →
«Скачать модель…»**, выбрать из списка, нажать кнопку. Никаких `optimum-cli`, никакой
конвертации и никаких команд Python: в списке готовые **OpenVINO IR** сборки.

| Модель | Размер | Комментарий |
|---|---|---|
| `InternVL2-1B-int4-ov` | ~0.8 ГБ | Рекомендуется: самая быстрая |
| `InternVL2-2B-int4-ov` | ~1.5 ГБ | Заметно точнее описывает экран |
| `Phi-3.5-vision-instruct-int4-ov` | ~2.3 ГБ | Хорошо читает интерфейсы |
| `InternVL2-4B-int4-ov` | ~2.3 ГБ | Ещё точнее, медленнее |
| `Qwen3-VL-4B-Instruct-int4-ov` | ~3 ГБ | Самая свежая, требовательная |

Источники те же три, что и у моделей Whisper (huggingface.co → hf-mirror.com →
modelscope.cn) и тот же докачивающий загрузчик: прерванная загрузка продолжается с уже
скачанных файлов. Если позже все источники окажутся недоступны — модель можно скачать
где угодно самому и подключить кнопкой **«Указать свою папку модели…»**; папка должна
содержать `openvino_language_model.xml/.bin`, `openvino_text_embeddings_model.*`,
`openvino_vision_embeddings_model.*`, токенизатор/детокенизатор и `config.json`.
Свою модель из любого HF-репозитория можно подготовить и вручную:

```bash
pip install "optimum[openvino]"
optimum-cli export openvino --model <repo> --weight-format int4 <папка>
```

Вместе с моделью, если его ещё нет, ставится портативный Python с `openvino-genai` —
тот же, что используется для расшифровки на NPU/GPU.

> **Чего ждать от маленькой модели.** Замеры на этой машине, InternVL2-1B int4:
> NPU скомпилировать модель **не смог** (`Found 80 duplicated names`) — автоматически
> ушло на Arc iGPU, загрузка 10 с, дальше ~4,5 с на кадр. Английский слайд описывается
> прилично, но **русский экран модель не читает и начинает выдумывать** (на слайде про
> планы команды она «увидела» поле ввода и политику приватности). Текст всё равно берётся
> из OCR — он точен; выдумывать может только описание. Поэтому: для русских созвонов
> полагайтесь на OCR, а описание экрана доверяйте либо более крупной модели
> (2B/4B), либо режиму `ocr+keyframes`, где кадры смотрит Claude. Промпт настраивается
> (`ScreenVlmPrompt`) и по умолчанию прямо запрещает домысливать.

Настройки в `settings.json`: `ScreenUnderstanding` (`off` | `ocr` | `ocr+keyframes` |
`vlm`), `ScreenTextAfterCall`, `ScreenOcrLanguages`, `ScreenSceneThreshold`,
`ScreenSampleFps`, `ScreenMinSecondsBetweenFrames`, `ScreenMaxKeyFrames`,
`ScreenOcrUpscale` (>1 помогает мелкому тексту), `ScreenKeyFrameMaxWidth`,
`ScreenVlmModelDir`, `ScreenVlmDevice`, `ScreenVlmMaxTokens`, `ScreenVlmPrompt`.

Отмена — тем же «⏹ Остановить»: ffmpeg убивается вместе с деревом процессов, сайдкар
закрывается, временные кадры удаляются.

### Расшифровка через Whisper

Подменю **«Расшифровка (Whisper)»**:

```
Расшифровать последнюю запись
Расшифровать все новые
Центр расшифровки…                 ← гибкий запуск и перерасшифровка (см. ниже)
⏹ Остановить расшифровку           ← останавливает все устройства, чистит недописанное
─────────
Режим ▸  ● Распределять задачи по устройствам  ○ Сравнение: каждую запись на всех
CPU: whisper.cpp large-v3 ▸        ← [✓] Участвует │ модели для CPU
GPU: OpenVINO turbo — выкл. ▸      ← [ ] Участвует │ модели для GPU
NPU: OpenVINO turbo — выкл. ▸      ← [ ] Участвует │ модели для NPU (large-v3 — «не работает на NPU»)
Языки транскрипции ▸ / Что расшифровывать ▸
─────────
Проверить установку Whisper / Установить whisper.cpp… / Установить OpenVINO… / Открыть лог
```

### Устройства, модели и режимы

Каждое устройство — отдельный **исполнитель** со своим движком и моделью и переключателем
«Участвует в расшифровке». В подменю устройства видны только модели, которые на нём
работают:

| Устройство | Модели |
|---|---|
| **CPU** | всё, что было раньше: whisper.cpp с любыми скачанными ggml-моделями (или openai-whisper на PATH); плюс OpenVINO-модели на CPU |
| **GPU** (Arc) | OpenVINO: turbo, large-v3, medium |
| **NPU** (AI Boost) | OpenVINO: turbo, medium. large-v3 виден серым — «не работает на NPU» (проверено). Пункт «Проверить заново модели "не работает на NPU"» снимает отметки (например, после обновления драйвера) |

Не скачанная модель помечена «— скачать» — выбор запускает загрузку. **По умолчанию
включён только CPU с whisper.cpp** — ровно прежнее поведение.

**Режимы:**
- **Распределять задачи** — каждая пара «запись × язык» расшифровывается один раз, задачи
  раскидываются по включённым устройствам, чтобы вся пачка закончилась как можно раньше.
- **Сравнение** — каждую запись расшифровывает каждое включённое устройство своей моделью
  (одно и то же — на CPU, GPU и NPU одновременно).

**Как распределяются задачи.** Одно устройство никогда не делает две задачи сразу; разные
устройства работают параллельно. Планировщик учитывает скорость каждой пары «устройство +
модель» (стартует с замеров и уточняется после каждой задачи —
`%APPDATA%\WorkHub\transcription_stats.json`), время первой компиляции модели и то, **насколько
работа устройства тормозит остальные** (у них общий кристалл, питание и память:
whisper.cpp на CPU замедляет GPU примерно в 1.5×, NPU почти не мешает). Свободное устройство
берёт задачу (самую длинную из подходящих), только если от этого вся пачка закончится
раньше, — поэтому медленный CPU не «утаскивает» запись, которую GPU сделал бы в 17 раз
быстрее. Когда CPU всё же работает вместе с GPU/NPU, whisper.cpp берёт меньше потоков
(`WhisperCppThreadsParallel`, по умолчанию «все ядра − 4»).

**Сбои.** Устройство, которое не может выполнить модель (например, large-v3 на NPU),
выбывает из прогона, его задача уходит другим. Временный сбой (NPU «завис»:
`DEVICE_LOST` — на этом драйвере случается, когда NPU работает одновременно с GPU) не
считается несовместимостью: в режиме распределения задача возвращается в очередь и её
берёт лучшее свободное устройство (после второго сбоя на том же устройстве — только
другие); в режиме сравнения — один повтор на том же устройстве. Кэш модели при этом не
удаляется.

**Замер распределения** (5 записей: 60 + 355 + 473 + 481 + 845 с ≈ 37 мин аудио, ru):

| Устройства (модель) | Время |
|---|---|
| только GPU (turbo) | 79.8 с |
| GPU + NPU + CPU, простое «кто свободен — берёт» (первая версия) | 89 с — хуже: CPU тормозил GPU |
| GPU + NPU + CPU, планировщик с учётом скорости и взаимного торможения | **60.7 / 61.8 с** (−24%): GPU — 4 записи, NPU — 1–2, CPU сам не брал |

Вывод для этого железа: для пачки записей выигрыш даёт пара **GPU + NPU**; CPU с
whisper.cpp полезен в сравнении и как запасной, но в распределении рядом с GPU почти не
нужен — планировщик это учитывает сам.

**Имена файлов** — с устройством, движком и моделью:

```
call_2026-09-25_10-24-49_ru_CPU-wcpp-large-v3.txt
call_2026-09-25_10-24-49_ru_GPU-ov-turbo.txt
call_2026-09-25_10-24-49_ru_NPU-ov-medium.txt
```

Старые файлы `call_…_ru.txt` не трогаются и считаются расшифровкой. «Расшифровать все
новые» берёт записи, у которых для языка **нет ни одной** расшифровки (ни старой, ни с
меткой); «Расшифровать последнюю» перезаписывает файлы с метками включённых устройств.

### Центр расшифровки

Окно для гибких запусков и **перерасшифровки** старых записей другими устройствами/моделями:

- слева — все записи с длительностью и уже имеющимися расшифровками по языкам
  (`ru: старый, GPU-ov-turbo; en: CPU-wcpp-large-v3`), кнопки «Без расшифровки / Все /
  Снять»;
- справа — режим, **сетка «устройство × модель»** (в сравнении можно отметить несколько
  моделей на одном устройстве — они пойдут на нём по очереди; в распределении — одна на
  устройство), языки, канал, «перезаписывать расшифровки с той же меткой»;
- во время работы видно, что делает каждое устройство и сколько уже идёт, общий прогресс
  и короткий лог.

Выбор в окне действует только на этот запуск (трей не меняется); кнопка **«Сделать
настройками по умолчанию»** переносит его в трей.

**Что расшифровывать (каналы).** Запись стерео: ваш микрофон — левый канал, собеседники —
правый. Подменю **«Что расшифровывать»** позволяет выбрать источник:
- **Мою речь и собеседников** (по умолчанию) — оба канала сводятся в моно;
- **Только собеседников (без моего микрофона)** — берётся правый канал, ваш голос
  игнорируется;
- **Только меня** — левый канал.

Выбранный канал извлекается во временный моно-WAV (через NAudio, без ffmpeg) и подаётся
Whisper; временный файл удаляется после расшифровки. На моно-записи (микрофона не было)
делить нечего — берётся как есть.

**Языки.** По умолчанию включены два — **Русский** и **English**. Whisper проходит по
записи отдельно для каждого включённого языка и создаёт по отдельному файлу (`_ru_…`,
`_en_…`); это отдельные задачи — в режиме распределения их делают разные устройства
одновременно. Любой язык можно отключить в «Языки транскрипции». Файл, который пишется
прямо сейчас, из расшифровки исключается.

### Защита от галлюцинаций на тишине (VAD)

Whisper на тихих/шумных участках склонен выдумывать текст (например `Субтитры создавал
DimaTorzok`, повторы `Thank you.`, теги `*Music*`). Чтобы этого не было, хаб использует
**VAD** (Voice Activity Detection, silero): сначала находит участки с реальной речью и
подаёт Whisper только их — тишина не обрабатывается вовсе. Побочный плюс: расшифровка
быстрее.

VAD-модель (~0.9 МБ) скачивается автоматически при установке движка. Настройки в
`settings.json`: `WhisperUseVad` (вкл/выкл), `WhisperVadModel` (путь), `WhisperVadThreshold`
(0.5 по умолчанию у whisper.cpp; хаб ставит 0.6 — строже, меньше ложной речи на шуме).

### Скорость (потоки CPU)

whisper.cpp по умолчанию берёт всего 4 потока. Хаб задаёт число потоков сам: `0` = все
логические ядра (замер на Core Ultra 7 255H: 16 потоков ≈ **в 1.9× быстрее** 4). Кап —
поле `WhisperCppThreads` в `settings.json` (например `10`, если хочешь оставить ядра
под другую работу во время расшифровки).

### Движок ставится сам (при первой расшифровке)

Если при попытке расшифровки движок не найден, хаб откроет окно установки и предложит
**скачать портативный whisper.cpp** — один exe, **без установки, без Python, без ffmpeg**,
без прав администратора. Хаб сам:

1. находит свежую Windows-сборку whisper.cpp на GitHub и качает её;
2. качает выбранную ggml-модель (base/small/medium/…) с Hugging Face;
3. кладёт всё в `%APPDATA%\WorkHub\tools\whispercpp` и прописывает пути в настройки.

Детект и предложение установки срабатывают при нажатии «Расшифровать…», либо вручную
через пункт меню **«Установить / настроить Whisper…»**.

**Если Hugging Face заблокирован** (бывает в корпоративных сетях): бинарь всё равно
скачается с GitHub, а модель можно скачать вручную (кнопка «Скачать модель (браузер)»
ведёт на страницу моделей) и подключить кнопкой **«Указать модель (.bin)…»**.

### Движок OpenVINO (NPU / GPU) — по желанию

Второй движок распознавания, в дополнение к whisper.cpp (он остаётся движком CPU **по
умолчанию**). Включается выбором OpenVINO-модели у устройства GPU / NPU (или CPU) в
«Расшифровка → GPU / NPU / CPU». Каналы, языки, «⏹ Остановить расшифровку» работают с
обоими движками одинаково.

**Как устроено.** Intel **OpenVINO GenAI `WhisperPipeline`** в отдельном процессе-сайдкаре
на портативном Python (`ov_whisper.py` зашит в exe и выкладывается рядом с Python). Хаб
передаёт ему WAV (или временный моно-WAV выбранного канала) и язык, сайдкар пишет `.txt`
(через `.part` → rename, так что недописанный файл никогда не выглядит готовым).
Почему сайдкар, а не C#-биндинги: готовых .NET-биндингов у GenAI нет (есть только C API);
отдельный процесс изолирует хаб (и запись созвонов!) от падений/зависаний NPU-драйвера, а
«Стоп» просто убивает процесс — компиляцию модели на NPU/GPU иначе не прервать.

**Несовместимость модели и устройства** запоминается сайдкаром
(`tools\openvino\cache\<модель>\device_health.json`, с привязкой к модели, версии OpenVINO и
драйвера NPU): такая модель показывается у устройства серым «не работает на NPU», а кэш
неудачной компиляции удаляется. Временные сбои (`DEVICE_LOST`, нехватка памяти) не
запоминаются. Сам сайдкар умеет и `--device AUTO` (NPU → GPU → CPU с фолбэком), но хаб
теперь всегда передаёт конкретное устройство — фолбэк делает планировщик.

Что, где и сколько делалось — в логе **«Открыть лог расшифровки»**
(`%APPDATA%\WorkHub\logs\transcription.log`: строки с меткой исполнителя `[GPU-ov-turbo]`,
весь вывод движков, сбои с причиной, время загрузки и распознавания, RTF).

Первый запуск на NPU/GPU компилирует модель (GPU ~10–20 с, NPU ~1.5–5 мин в зависимости от
модели); результат кэшируется в `tools\openvino\cache\<модель>\<устройство>`, дальше загрузка —
секунды. Кэш одной модели на одном устройстве — 0.5–3 ГБ; кэш устройства, которое не
справилось с моделью, удаляется сразу. Папку `cache` можно удалить целиком в любой момент —
она пересоздастся (но NPU для large-v3 тогда один раз попробуется заново).

**Установка (один раз, без админа и без системного Python)** — «Установить / настроить
OpenVINO…» (или автоматически при выборе движка). Всё в `%APPDATA%\WorkHub\tools\openvino`:
1. `uv.exe` с GitHub (astral-sh/uv, ~18 МБ);
2. портативный CPython 3.12 (python-build-standalone, GitHub, ~20 МБ) и приватный venv;
3. `openvino-genai==2026.4.*` + numpy с PyPI (~100 МБ); итого ~360 МБ на диске;
4. готовая IR-модель **`OpenVINO/whisper-large-v3-turbo-int8-ov`** (~0.8 ГБ, по умолчанию;
   см. сравнение моделей ниже), уже сконвертированная Intel, поэтому torch/optimum не нужны.
   Источники по очереди: huggingface.co → hf-mirror.com → modelscope.cn. Файл считается
   скачанным, только если размер точно совпал с источником (у зеркал бывают разные
   ревизии — xml/bin из разных ревизий не смешиваются).

uv сначала ходит напрямую, при неудаче — через системный прокси (включая SOCKS-запись
`socks=host:port` из настроек Windows, которую uv сам не понимает).

**Если все источники модели заблокированы** — скачайте папку модели вручную (любой из
трёх сайтов, репозиторий `OpenVINO/whisper-large-v3-turbo-int8-ov`, все файлы
`openvino_*.xml/.bin`, `*.json`, `merges.txt`, `vocab.json`) и укажите её кнопкой
**«Указать папку модели…»**. Или сконвертируйте сами на машине с доступом к HF:

```bash
pip install "optimum-intel[openvino]"
optimum-cli export openvino --model openai/whisper-large-v3-turbo --weight-format int8 whisper-large-v3-turbo-int8-ov
```

Настройки в `settings.json`: `TranscriptionEngine` (`whispercpp` | `openvino`),
`OpenVinoDevice` (`AUTO` | `NPU` | `GPU` | `CPU`), `OpenVinoPython`, `OpenVinoModelDir`,
`OpenVinoModelRepo`.

**Модель OpenVINO** — **«Расшифровка → Модель OpenVINO»**: **large-v3-turbo int8** (по
умолчанию), large-v3 int8, medium int8. Ещё не скачанная модель докачивается через окно
установки.

**Замеры** (Core Ultra 7 255H, Arc 140T, NPU3720 / драйвер 32.0.100.4778, OpenVINO 2026.4;
реальный созвон, язык ru, оба канала; время — весь вызов, включая загрузку модели из кэша):

| Движок / модель / устройство | 60 с аудио | 355 с аудио | распознавание 355 с |
|---|---|---|---|
| whisper.cpp large-v3 (fp16), CPU 16 потоков, VAD | 57.1 с | 242.7 с | — |
| OpenVINO large-v3 int8, **GPU** | 16.4 с | 44.3 с | 37.5 с (RTF 0.11) |
| OpenVINO large-v3 int8, CPU | 21.0 с | — | 16.2 с на 60 с (RTF 0.27) |
| OpenVINO large-v3 int8, NPU | ✗ ошибка драйвера → фолбэк GPU | | |
| OpenVINO large-v3-turbo int8, **GPU** | 5.5 с | **14.5 с** | 12.4 с (RTF 0.03) |
| OpenVINO large-v3-turbo int8, **NPU** | 13.2–18.0 с | 44.3 с | 29.5 с (RTF 0.08) |
| OpenVINO medium int8, GPU | 9.2 с | 31.2 с | 22.8 с (RTF 0.06) |
| OpenVINO medium int8, NPU | 17.5 с | — | 46.8 с (RTF 0.13) |

Первая компиляция (один раз, потом кэш): large-v3 — GPU ~15–20 с, NPU ~4.5–5 мин (и всё
равно падает); turbo — GPU ~10 с, NPU ~3 мин; medium — GPU ~12 с, NPU ~1.5 мин. Во время
компиляции под NPU процесс занимает до ~8 ГБ ОЗУ.

Выводы:
- **large-v3 на NPU не работает** на этом железе/драйвере
  (`ZE_RESULT_ERROR_INVALID_NATIVE_BINARY` при исполнении; одинаково на OpenVINO 2026.1 и
  2026.4, с компилятором драйвера и плагина). NPU как таковой исправен — turbo, medium и
  tiny на нём работают. В «Авто» это обрабатывается фолбэком на GPU.
- Самый быстрый вариант — **turbo на GPU** (~17× быстрее whisper.cpp). NPU с turbo
  медленнее GPU, зато не грузит ни CPU, ни видеокарту (и экономнее по питанию).
**Качество** (тот же созвон 355 с; пословное расхождение с текстом whisper.cpp large-v3 —
ручной эталонной расшифровки нет, так что это ориентир, а не точный WER):

| Модель OpenVINO | слов (whisper.cpp: 518) | расхождение с whisper.cpp | GPU vs NPU между собой |
|---|---|---|---|
| large-v3 int8 | 499 | 23.4% | — (NPU не работает) |
| **large-v3-turbo int8** | 479–483 | 27.6% | 9.9% |
| medium int8 | 581–605 | 40–45% | 25.6% |

- whisper.cpp large-v3 (fp16) — по-прежнему лучший по качеству: пунктуация, точнее
  термины. OpenVINO-модели пишут без пунктуации (кроме medium) и чаще ошибаются в
  именах/терминах. Для важных созвонов, где не жалко 4 минут, — whisper.cpp; для
  быстрых расшифровок — OpenVINO turbo.
- **turbo** — ближе всех к large-v3 из тех, что работают на NPU, и стабильна: на GPU и NPU
  даёт почти один и тот же текст. Поэтому она модель по умолчанию.
- **medium** ставит пунктуацию, но добавляет фразы, которых не слышит ни одна другая
  модель (и сама medium на GPU и на NPU пишет в этих местах разное) — признак
  выдумывания. Не рекомендуется.
- Зацикливаний на паузах («×200», «Субтитры создавал…») не было ни у одной модели (VAD у
  OpenVINO-движка нет).

## Модуль 2. Автозапуск программ

При старте хаб запускает заранее настроенные программы/ярлыки. Настройка — в меню
**«Автозапуск программ» → «Настроить список…»**:

- **Добавить…** — выбрать `.exe`, `.lnk`, `.bat`, `.cmd` или любой файл.
- **Вкл** (галочка) — включён ли пункт.
- **От админа** (галочка) — запускать с повышением прав (**UAC** спросит подтверждение
  на каждый такой пункт — это ограничение Windows при запуске из неэлевированного
  процесса).
- **Аргументы** — параметры командной строки (опционально).
- **Запустить сейчас** — проверить список немедленно.
- Галочка **«Запускать список при старте хаба»** — включает автозапуск на старте.

Настройки хранятся в `%APPDATA%\WorkHub\settings.json`.

> Обычный запуск идёт через shell (поэтому работают ярлыки и документы). Запуск «от
> админа» использует `runas` (UAC). Полностью «тихого» запуска от админа без UAC штатно
> не бывает; если нужно без подтверждения — это делается через Планировщик задач с
> отдельной задачей на каждую программу (можно добавить, если понадобится).

## Модуль 3. Авто-реконнект GlobalProtect

Периодически проверяет **общий интернет**; если он пропал (после нескольких неудачных
проб подряд) — просит GlobalProtect переустановить туннель. **Выключен по умолчанию**,
включается в меню **GlobalProtect → «Авто-реконнект при потере интернета»**.

**Как переподключает.** UI GlobalProtect owner-drawn и недоступен для UI Automation
(пункты меню не читаются, `Invoke` не поддерживается). Поэтому клик делается по
координатам, **привязанным к реальным прямоугольникам окна** (не к абсолютным
пикселям, поэтому переживает перемещение окна/другое разрешение/DPI):

1. находит окно `GlobalProtect` (или открывает `PanGPA.exe`);
2. кликает гамбургер-меню (доля от прямоугольника окна);
3. читает прямоугольник попап-меню `#32768` в рантайме;
4. кликает **верхний пункт** — это `Refresh Connection` (когда подключён) или
   `Connect` (когда отключён); оба переустанавливают туннель, и оба вверху — так мы
   никогда не попадём в `Disconnect`.

**Защита от «долбёжки»:** антидребезг на «интернет пропал», кулдаун между попытками
(90 сек по умолчанию) и расширение кулдауна после нескольких безуспешных попыток.
Успех/неуспех — во всплывающих уведомлениях; ручная проверка — «Обновить подключение
сейчас».

**Настройки** (в `settings.json`): интервал пробы, порог неудач, кулдаун, доли
координат гамбургера/пункта, список URL для пробы, путь к `PanGPA.exe`.

> ⚠️ Остаточная хрупкость: если Palo Alto в новой версии поменяет порядок/раскладку
> пунктов меню — сместятся доли (правятся в `settings.json`). И помни: на корпоративной
> машине переподключения VPN обычно логируются — согласуй с IT, если нужно.
